# Claude Code ベストプラクティス

このリポジトリに導入した Claude Code の設定が「何のためにあるのか」を説明する文書。

> **このファイルは `CLAUDE.md` から `@` インポートしないこと。**
> インポートすると毎セッション全文がコンテキストに読み込まれ、恒久的にトークンを消費する。
> `docs/` に置いたまま「読みたいときだけ読む」のが正しい。

---

## 1. なぜ CLAUDE.md が効かないことがあるのか

`CLAUDE.md` は**毎セッションの開始時に全文がコンテキストに載る**。しかもシステムプロンプトではなく
ユーザーメッセージとして届くので、**強制ではなくお願い**である。

ここから2つの帰結が出る。

1. **長くすると恒久的にトークンを食う。** 300行の CLAUDE.md は、その後の会話すべてに
   その分の重りが付く。
2. **長くすると遵守率が下がる。** 重要なルールがノイズに埋もれる。
   「ルールを書いたのに守ってくれない」ときは、たいていファイルが長すぎるのが原因。

公式の推奨は **200行以下**。このリポジトリの `CLAUDE.md` は約70行にしてある。

### 取捨選択の判断基準

各行について「**この行を消したら Claude はミスをするか？**」と問う。Noなら消す。

| ✅ 書く                    | ❌ 書かない                           |
| -------------------------- | ------------------------------------- |
| 推測できないコマンド       | コードを読めば分かること              |
| **ツール既定と違う**規約   | 一般的な言語・フレームワークの慣習    |
| 環境の癖（必須の環境変数） | 詳細なAPIドキュメント（リンクで十分） |
| 落とし穴・直感に反する挙動 | 頻繁に変わる情報                      |
| ブランチ / PR の作法       | ファイルごとの説明                    |
| プロジェクト固有の設計判断 | 「きれいなコードを書く」的な自明な話  |

このリポジトリで言えば、

- ✅「Chakra UI は v2 であって v3 ではない」
  — v3 の知識で書くと確実に壊れるのに、コードからは読み取りにくいので必須
- ✅「`Post.image_url` は URL ではなく Storage のパス」
  — 型は `string` としか言っておらず、名前が嘘をついているので必須
- ❌「コンポーネントは `src/components/` にある」
  — `ls` すれば分かる。書く価値がない

### うまくいっているかの見分け方

- 同じ指摘を2回したのにまだ直らない → ファイルが長すぎてルールが埋もれている
- CLAUDE.md に書いてあることを Claude が質問してくる → 書き方が曖昧
- `/context` を実行すると **Memory files** にロード済みのファイルが出る。まずここを確認する

## 2. 5層の使い分け（最重要）

CLAUDE.md に全部書こうとするのが最大の失敗パターン。「**何を保証したいか**」で層を分ける。

| 保証したいこと               | 使う仕組み                         | 読み込まれるタイミング                 |
| ---------------------------- | ---------------------------------- | -------------------------------------- |
| 常に効いてほしい事実         | `CLAUDE.md`                        | **毎セッション全文**（トークン固定費） |
| 特定ファイルの時だけ効く規約 | `.claude/rules/*.md` + `paths:`    | 該当ファイルを読んだ時だけ             |
| 手順・チェックリスト         | `.claude/skills/<name>/SKILL.md`   | 呼ばれた時だけ                         |
| **必ず**実行されないと困る事 | `.claude/settings.json` の `hooks` | 確定実行（LLMの判断に依らない）        |
| 文脈を汚さず調査／レビュー   | `.claude/agents/*.md`              | 委譲時に別コンテキストで               |

合言葉は「**強制したいならフック、文脈知識ならスキル、委譲境界ならサブエージェント、
常時の指針なら CLAUDE.md（短く）**」。

### `.claude/rules/` — 条件付きで読み込まれる規約

frontmatter に `paths:` を書くと、**そのパターンに一致するファイルを Claude が読んだときだけ**
ルールが読み込まれる。CLAUDE.md を短く保ちながら、詳しい規約を持てる。

```markdown
---
paths:
  - "src/**/*.tsx"
  - "src/theme.ts"
---

# Chakra UI v2 の規約

...
```

`paths:` が無いルールは無条件に毎回読み込まれる（＝ CLAUDE.md と同じ扱い）ので、
基本は必ず `paths:` を付ける。

### `.claude/skills/` — 手順を再利用する

同じ指示を2回コピペしたら、それはスキルにすべきサイン。
CLAUDE.md の一節が「事実」ではなく「手順」に育ってきたときも同じ。

```markdown
---
name: verify
description: 全チェックを順に実行し、失敗があれば根本原因を直して緑になるまで繰り返す
allowed-tools: Bash(npm run *)
---

1. `npm run lint`
2. `npm run typecheck`
   ...
```

- `/verify` のようにスラッシュコマンドとして呼べる（スキルとカスタムコマンドは統合された）
- `description` が的確だと、Claude が自分で「今これが必要だ」と判断して読み込む
- `disable-model-invocation: true` を付けると**手動でしか起動しない**。
  push や PR 作成のような副作用のある手順には必ず付ける
- **`## よくある失敗（gotchas）` セクションを必ず書く。**
  正常系の手順よりも、こちらの方が信頼性に効く

### `.claude/settings.json` の `hooks` — 唯一の「強制」

CLAUDE.md の指示は守られないことがあるが、フックはライフサイクルイベントで**必ず実行される**。
「毎回やってほしいこと」は CLAUDE.md に書かずフックにする。書かない分トークンも浮く。

このリポジトリには3つ入れてある。

| フック                 | イベント                      | 何をするか                                                             |
| ---------------------- | ----------------------------- | ---------------------------------------------------------------------- |
| 依存の自動インストール | `SessionStart`                | `node_modules` が無ければ `npm ci`。新しいコンテナで毎回詰まるのを防ぐ |
| 自動整形               | `PostToolUse` (`Edit\|Write`) | 編集したファイルに `prettier --write`                                  |
| **検証の強制**         | `Stop`                        | ソースを変更したのに検証せずターンを終えようとしたら止める             |

3つ目が後述するループエンジニアリングの入口。

### `.claude/agents/` — 別コンテキストで動く担当者

コンテキストは有限で、埋まるほど性能が落ちる。**調査とレビューはサブエージェントに投げる**のが
一番効く節約になる。読み込んだ大量のファイルは向こうのコンテキストに溜まり、
こちらには要約だけが返ってくる。

このリポジトリの `diff-reviewer` は「差分と基準だけを見る第三者」。実装したセッション自身に
採点させないためにある。書いた本人は自分の推論に引きずられるので、新しいコンテキストの方が
素直に欠陥を見つける。

## 3. ループエンジニアリング

2026年6月、OpenClaw 作者の Peter Steinberger 氏の
「**You should be designing loops that prompt your agents**（プロンプトを書くのではなく、
エージェントを駆動するループを設計しろ）」という投稿から広まり、Google の Addy Osmani 氏が
体系化した考え方。Claude Code 開発者の Boris Cherny 氏は
「2026年に入って自分では1行もコードを書いていない、スマホで日に何十本ものPRを承認しているだけ」
と述べている。

### 出発点の原理

> **Claude は「作業が終わったように見えたら」止まる。**

合否を出す仕組みがないと、「終わったように見える」が唯一の停止信号になり、
**あなた自身が検証ループになる**。すべてのミスが、あなたが気づくまで放置される。

逆に、Claude が自分で走らせて結果を読める合否——テストスイート、ビルドの終了コード、
Lint、スクリーンショットの比較——を渡せば、ループが自分で閉じる。
Claude が作業し、チェックを走らせ、結果を読み、通るまで直す。

**だからこのリポジトリでは、設定ファイルを置く前に `typecheck` スクリプトと CI を用意した。**
検証手段がないままループだけ回すのは、壊れたまま回り続ける最悪の状態になる。

### 停止条件の4段階

| 手段                        | 次のターンが始まる条件 | 止まる条件                        | 使いどころ                |
| --------------------------- | ---------------------- | --------------------------------- | ------------------------- |
| プロンプト内で指示          | —                      | Claude の判断                     | 今すぐ使える最小形        |
| **`/goal <条件>`**          | 前のターンが終わったら | **別モデルが条件成立と判定**      | セッション単位の自走      |
| **`Stop` フック**           | 前のターンが終わったら | 自分のスクリプト／プロンプト      | リポジトリ全体に恒久適用  |
| **`/loop [間隔] [prompt]`** | 時間経過               | `Esc`、または Claude が完了と判断 | PR の面倒見・デプロイ監視 |

下に行くほど「設定の手間」と引き換えに「あなたの注意力」が要らなくなる。

#### `/goal` — 条件が満たされるまで自走する

```
/goal npm run lint と npm run typecheck と npm run test がすべて exit 0 になる。既存のテストは変更しない。20ターン経過したら停止する
```

毎ターン終了後に小型高速モデル（既定は Haiku）が条件の成否を判定し、未達なら
その理由を次のターンの指示として Claude に返す。達成すると自動的に解除される。

- `/goal` だけで現在の状態（条件・経過時間・ターン数・トークン消費・直近の判定理由）が見られる
- `/goal clear` で解除
- **判定モデルはツールを実行できず、会話に出てきた内容しか見られない。**
  だから「Claude 自身の出力で証明できる条件」を書く必要がある。
  「テストが通る」は Claude がテストを実行してその出力が会話に載るので判定できる

#### `/loop` — 時間間隔で回す

```
/loop 10m CI が通ったか確認し、レビューコメントがあれば対応して
/loop 20m /verify
/loop                      ← 間隔もプロンプトも省略
```

間隔を省略すると Claude が状況を見て自分でペースを決める（ビルド中は短く、静かになったら長く）。
プロンプトも省略すると `.claude/loop.md` の内容が使われる（無ければ組み込みのメンテナンスプロンプト）。

- 止めるのは `Esc`
- 再帰的なタスクは **7日で自動失効**する（忘れたループが延々と回るのを防ぐため）
- セッションを閉じると止まる。マシンに依存せず回したいなら Routines か GitHub Actions

このリポジトリの `.claude/loop.md` は「やりかけの作業 → PR の面倒見 → `/verify` → 異常なしなら1行報告」
という順序にしてある。

### 良い停止条件の書き方

長いターン数を耐える条件には、だいたい次の4つが入っている。

1. **測定可能な終了状態が1つ** — テスト結果、ビルドの終了コード、ファイル数、キューが空
2. **どう証明するかの明示** — 「`npm test` が exit 0 で終わる」「`git status` がクリーン」
3. **変えてはいけない制約** — 「他のテストファイルは変更しない」
4. **上限** — 「20ターン経過したら停止する」

### アンチパターン

- **検証手段がないままループを回す。** 最悪。壊れたまま回り続ける
- **条件が曖昧。**「きれいなコードになるまで」は判定不能
- **上限がない。** 必ずターン数か時間の節を入れる
- **レビュアーの指摘を全部潰しにいく。** 「ギャップを探せ」と言われたレビュアーは、
  健全なコードでも何かしら見つけてくる。全部対応すると過剰な抽象化と防御的コードで
  肥大化する。**正しさと要件に関わるものだけ**直す。
  このリポジトリの `diff-reviewer` にはその旨を明記してある
- **`Stop` フックがうるさいと感じたら外していい。** `.claude/settings.json` の `Stop` ブロックを
  削除するか、`.claude/settings.local.json`（gitignore 済み）で上書きする。
  なお8回連続でブロックすると Claude Code 側が自動的に解除するので、無限ループにはならない

## 4. コンテキスト管理

ほとんどのベストプラクティスは、たった1つの制約から導かれる。
**コンテキストウィンドウはすぐ埋まり、埋まるほど性能が落ちる。**

- **`/clear` を作業の切れ目で使う。** 無関係なタスクを同じセッションで続けると、
  前のタスクの残骸が邪魔をする
- **同じ指摘を2回して直らなければ、`/clear` して書き直す方が速い。**
  失敗した方針で汚れたコンテキストを引きずるより、学んだことを盛り込んだ新しいプロンプトの方が強い
- **調査はサブエージェントに投げる。**「サブエージェントを使って〜を調べて」と言えば、
  大量のファイル読み込みは向こうのコンテキストで消化される
- **`/context`** で今何が読み込まれているかを確認できる
- **`/rewind`（`Esc` 2回）** でコードと会話を巻き戻せる。
  「危なそうな方針を試させて、ダメなら巻き戻す」が安く済む

## 5. 日々の進め方

### 探索 → 計画 → 実装 → 検証 → コミット

1. **探索**（プランモード）— 「`src/supabase` を読んで、投稿の保存の流れを理解して」
2. **計画**（プランモード）— 「投稿の削除機能を追加したい。どのファイルが変わる？計画して」
3. **実装** — プランモードを抜けて実行
4. **検証** — `/verify`
5. **コミット** — `/pr-ready`

小さい変更（タイポ、ログ1行、リネーム）にプランモードは要らない。
**1文で差分を説明できるなら計画は飛ばす。**

### 大きめの機能は自分をインタビューさせる

```
[機能の概要] を作りたい。AskUserQuestion ツールを使って詳細に私にインタビューして。
技術的な実装、UI/UX、エッジケース、懸念、トレードオフについて聞いて。
自明な質問はせず、私が考えていない難しい部分を掘って。
全部カバーできたら SPEC.md に完全な仕様を書いて。
```

仕様が固まったら**新しいセッション**で実装する。コンテキストが実装だけに集中する。

### 具体的に書く

| ❌                           | ✅                                                                                                                                 |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 「foo.ts のテストを書いて」  | 「foo.ts の、ログアウト状態のエッジケースをカバーするテストを書いて。モックは避けて」                                              |
| 「ログインのバグを直して」   | 「セッションタイムアウト後にログインが失敗する。`src/auth/` のトークン更新まわりを見て。再現する失敗テストを先に書いてから直して」 |
| 「ダッシュボードを良くして」 | 「[スクショ] この通りに実装して。結果のスクショを撮って元と比較し、差分を列挙して直して」                                          |

## 6. このリポジトリに入っているもの

| ファイル                            | 対応する概念                                                                           |
| ----------------------------------- | -------------------------------------------------------------------------------------- |
| `CLAUDE.md`                         | 常時の指針（約70行に抑えてある）                                                       |
| `.claude/rules/chakra-ui-v2.md`     | `.tsx` を触るときだけ読まれる Chakra v2 の規約と配色パレット                           |
| `.claude/rules/supabase.md`         | `src/supabase/**` を触るときだけ読まれるデータアクセス規約                             |
| `.claude/rules/testing.md`          | `__test__/**` を触るときだけ読まれるテスト規約                                         |
| `.claude/skills/verify/SKILL.md`    | **合否判定の定義。`/goal` も `loop.md` も CI もここを参照する**                        |
| `.claude/skills/pr-ready/SKILL.md`  | レビュー → 検証 → コミット → push の手順（手動起動のみ）                               |
| `.claude/skills/fix-issue/SKILL.md` | issue から PR までの手順（手動起動のみ）                                               |
| `.claude/skills/add-page/SKILL.md`  | ページ追加の手順。ルータ登録とテストのモック更新の漏れを防ぐ（手動起動のみ）           |
| `.claude/agents/diff-reviewer.md`   | 敵対的レビュー用のサブエージェント                                                     |
| `.claude/settings.json`             | 3つのフック（依存インストール／自動整形／検証の強制）と権限の許可リスト                |
| `.claude/loop.md`                   | 引数なし `/loop` のデフォルト動作                                                      |
| `.github/workflows/main.yml`        | PR で回る検証。以前は `main` への push でしか動かず、PR に一切チェックがかからなかった |

`.claude/settings.local.json` は gitignore 済み。個人的な上書きはそちらに書く。
